## Concrete implementation findings

1. **High: attempt reservation is not atomic with verifier execution.** `verification.py:124–132` reads and increments the store counter before the process-wide extraction lock at lines 196–203. Two verifier commands can both read the same remaining budget, both write the same next count, then run sequential BDS jobs. The server lock enforces one active extraction but does not enforce the total budget or distinct attempt IDs. Existing tests cover serial persistence, not concurrent reservation.

2. **Medium: observation cache can survive changes to interpretation code.** `tooling_identity` hashes bundled BDS assets, while the observation identity excludes `verification.py`, `raster.py` and an interpretation-policy version. The baseline run identity also does not include these modules. Changing ground/water/quality interpretation without changing BDS assets can return a previously serialized raster/status. Existing runtime proof only establishes the current cache hit behavior.

3. **Medium: verified-observation scoring ignores configured/rescored weights.** `cli.py:287` calls the evaluator, whose `_finish` in `terrain.py:91` calculates `.8*geometry + .1*biome_fit + .1*baseline_quality`. The verification route does not apply `cfg['scoring']` or `score_policy` afterward. Its saved `actual_partial_score` can disagree with the configured/rescored policy. It also reuses predicted biome fit and baseline quality, which need explicit component provenance in the actual evaluation.

4. **Medium: calibration includes square tile overscan.** `raster_from_columns` filters rows to requested bounds/lattice, but `calibrate_prediction` uses every unique raw column without that filter. Non-square/edge tiled requests can therefore include outside-request points in reported calibration sample sizes/metrics. The selected 128-square check has no such overscan, so its 256-column result is unaffected.

5. **Medium: CLI cannot explicitly retry a cached extraction failure and can stall behind cached top picks.** `retry_failed=True` exists only on the adapter API, not the verify-terrain parser/call. Selection caps its *number of records* to remaining attempts before accounting for cache hits; a cached top record can repeatedly consume the selection slot without consuming an attempt, preventing lower unverified picks under a small cap. With budget exhausted, CLI selects nothing even when cached observations could be reviewed. This is scheduler/retry usability, not baseline data loss.

6. **Medium: cleanup failure can violate the one-server invariant.** In `_extract_locked`'s finally block, `console.stop()` has no fallback if its command/wait raises, and the result-file write follows that call. A failed graceful stop can leave the container running, skip the final raw report write and release the extraction lock; a later call could then start another server. Existing successful clean-shutdown proofs do not exercise this adverse path. Docker subprocesses also generally lack explicit timeouts.

7. **Missing integration: overlap reuse and final Nether caching.** Each new footprint creates a fresh BDS world; exact-request reuse is not a chunk/tile cache shared across V1/V2 regions. Final Nether import validation neither uses the adapter identity nor persists an observation cache keyed by seed/anchor/settings/region. These are implementation requirements separate from the unavailable structure API.

8. **Missing cave behavior: uncertain refinement and completed failure artifacts.** Refinement candidates are only positive family observations (`caves.py:58`); missing/uncertain areas are not refined. `sample_caves` calls extraction without the terrain failure-record wrapper. A failing manual BDS cave invocation exits before the CLI writes its requested output JSON. No test currently establishes bounded uncertain refinement or provider-failure cave results.

## External generation/evidence gates

The stable Script API's unavailable `getGeneratedStructures` is an external capability limitation, not evidence of absent structures. Actual required Overworld and final Nether structure controls must come from a supported pinned-generation source or trustworthy imported fixture, then be integrated through complete source/settings/coverage identity. Proven natural ground and complete water semantics require both policy implementation and matching-runtime controls. Full formation connectivity/enclosure, V1/V2 independent ranking calibration, Dappled/Sulfur positives, positive/negative rare geometry controls and population accuracy remain unverified.

The selected runtime fixture establishes bounded extraction consistency, not exact natural-ground or full geometry qualification: seed `-1001562501133105644`, center `(1572,1012)`, bounds `[1508,948,1636,1076)`, spacing 8, 256 columns. It passed 81/81 finalized chunks and 568/568 snapshot/API probes in 20.8976 seconds, with baseline unchanged and a zero-extra-attempt cache hit. Ground-height MAE was 3.8046875 blocks, maximum 39, and 153 columns differed in height. Water/land proxy mismatch counts are the same **71/256** binary disagreements: predicted proxy water 99 versus observed exposed water 28. This is substantial local proxy disagreement, not population recall or a full fluid classifier validation. Readiness of 81 requested chunks in 2.8713 seconds (~28.2 requested chunks/s) is not sustained new-chunk generation throughput; peak container memory 331,935,744 bytes excludes Docker VM/host peaks.
